## 0. 대원칙 (불가침 원칙) — 🟡 일부 확정 (B·E·G)

> 가장 중요한 규칙으로, 솔버가 **하드 제약**으로 지키려 시도한다. 위배가 감지되면
> 조용히 넘어가지 않고 **경고 → 사용자 선택** 절차를 거친다(아래 워크플로우).
> 나머지 대원칙 후보(A·C·D·F)는 **파트장님이 정한 실제 병동 원칙을 파악한 뒤** 추가한다.

### 0.1 확정된 대원칙 (2026-07-21)

| # | 대원칙 | 내용 | 근거 |
|---|--------|------|------|
| **P1** | 나이트 후 휴식 (B) | N 다음날 **D/E/M 금지**(나이트 또는 오프만) + **N-OFF-D 금지** | 안전·회복 / 실측 0건 |
| **P2** | 하루 1근무 (E) | 각 간호사는 하루에 **근무/휴무 중 정확히 하나** | 물리적 원칙 |
| **P3** | 역회전 금지 (G) | **E 다음날 D 직접 배정 금지** (짧은 휴식 방지) | 실측 0건 |

### 0.2 대원칙 위배 시 워크플로우 (경고 + 사용자 선택)

대원칙 위반이 감지되면(주로 **수동 수정** 중, 또는 자동 생성이 대원칙을 만족 못할 때):

1. **경고창 표시** — 어떤 대원칙이 어디서(간호사·날짜) 위반됐는지 구체적으로 안내
2. 사용자가 선택:
   - **(가) 위배 감수하고 작성 진행** — 경고를 인지한 채 그대로 확정
   - **(나) 대안 3가지 제시받기** — 시스템이 위반을 해소하는 **대안 3안**을 제안 →
     사용자가 하나를 골라 자동 수정
3. 선택 결과를 근무표에 반영

> 설계 함의: 대원칙은 자동 생성 시 하드 제약으로 취급하되, **위반 감지 → 경고 →
> (진행 | 대안3안 중 택1)** 절차를 별도 모듈로 둔다. "무조건 생성 불가"가 아니라
> **사용자에게 통제권**을 주는 방식.

### 0.3 대원칙 승격 대기 (파트장 원칙 파악 후 결정)
- A 교대별·팀별 최소 인원 · C 신규·임신 나이트 금지 · D 사전 휴무 불가침 ·
  F 과로 방지 상한(연속근무≤5·연속나이트≤3·주근무≤6)
- 위 항목들은 현재도 **하드 제약**으로 적용하되, 불가침 '대원칙' 등급 승격은 보류.

## 1. 프로젝트 개요

3교대(+미드) 간호사 근무표(듀티표)를 제약조건 최적화로 자동 생성하는 웹 애플리케이션.
Google OR-Tools **CP-SAT** 솔버로 병동 고유 규칙을 만족하는 월간 근무표를 계산한다.

### 확정된 기본 요구사항 (요구사항 인터뷰 결과) — ✅

| 항목 | 내용 |
|------|------|
| 애플리케이션 형태 | 웹 앱 (우선 웹 화면 조회) |
| 지원 기기 | **모바일 + 데스크탑 둘 다 (반응형)** — 부서원=폰 위주, 파트장=데스크탑 위주 |
| 기술 스택 | Python (FastAPI + OR-Tools + Pydantic) |
| 교대 구조 | 3교대(D/E/N) **+ 미드(M)** |
| 비근무 코드 | 연차·공가·병가·Edu 등 표에 코드로 표시 |
| 병동 규모 | 약 16–25명 |
| 편성 주기 | 월 단위 (약 28–31일) |
| 회전 규칙 | 역회전(E→D, N→D 등) 금지, 순방향(D→M→E→N) 선호 |
| 간호사 속성 | 신규·임신 간호사 나이트 제외 |
| 월 운영 | 근무일/오프/나이트 균등, 사전 휴무 반영, 전월 말일 이어받기, 개인 오프/나이트 신청 |

## 2. 근무 코드 체계 — ✅(초안)

| 구분 | 코드 | 의미 | 스케줄링 취급 |
|------|------|------|----------------|
| 근무 | `D` | 데이 | 인원 계산 · 회전 대상 |
| 근무 | `M` | 미드 | 인원 계산 · 회전 대상 |
| 근무 | `E` | 이브닝 | 인원 계산 · 회전 대상 |
| 근무 | `N` | 나이트 | 인원 계산 · 회전 대상 |
| 근무 | `M/D` | **실제 미드**, 전산 표기 `D` | 커버리지·회전은 **미드(M)**, 기록·집계는 **D** |
| 근무 | `M/E` | **실제 미드**, 전산 표기 `E` | 커버리지·회전은 **미드(M)**, 기록·집계는 **E** |
| 휴무 | `O` | 오프 | 근무 아님(연속근무 리셋) |
| 비근무 | `연차`/`공가`/`병가`/`Edu` 등 | 사전 확정 휴무·비근무 | 오프처럼 취급 + 표에 코드 표시 |

> **M/D·M/E — 우리 병원 고유 정책 (중요)**: 실제 근무 시간대는 **미드(M)** 이지만,
> 병원 정책상 미드는 **근무교대 수당이 지급되지 않아** 전산에는 **D 또는 E로 신청**해야 한다.
> 그래서 표에 `M/D`(실제 미드·전산 D), `M/E`(실제 미드·전산 E)로 표기한다.
> **구현 함의**: 내부적으로 shift=M(미드)로 두고 `record_as`(D 또는 E) 속성을 별도로 가진다.
> - 인원 커버리지·회전·연속 규칙 → **미드(M)로 취급**
> - 근무시간·수당·전산 기록·집계 → **D 또는 E로 취급**
> - 화면 표시 → `M/D` / `M/E`
> (실제 손기록 표의 D/E/근무시간 집계는 이 정책 때문에 일부 편차가 있으나, 정책이 기준.)

> 미드(M) 근무 시간대·역할은 병동 상황(3장)에서 구체화.

## 3. 병동 상황 & 기능 범위 — 🟡 (팀 A안 확정, 세부 파트장 확인 대기)

> 사용자가 전달하는 실제 병동 운영 정보를 여기 축적하고, 그에 따라 **넣을 기능 / 뺄 기능**을
> 결정한다.

### 3.1 병동 운영 정보 (사용자 입력 축적)

**대상 병동: 61병동 (샘플)**
- 병실 약 15개: **601~614호 + 616호** (615호 없음)
- 병실을 **3개 팀**으로 분리 운영 (팀별 담당 병실 그룹)
- **팀 연속성 원칙**: 간호사는 가능하면 **한 팀 내에서 계속 근무** → 환자 파악에 유리.
  불가피한 경우에만 팀 변경 허용 → **소프트 제약**(가능하면 유지, 강제는 아님)

**팀 구성 (확정)**
- **3개 팀**, **팀당 약 7~8명** (전체 약 21~24명 규모)
- **교대별 팀별 최소 인원 필요** ✅ — 최소 인원 제약이 **전체가 아니라 팀 단위**.
  즉 각 교대(D/E/N/M)에 팀1·팀2·팀3 각각 최소 인원이 채워져야 함.

**명단 순서 = 경력·업무능력 순 (사용자 확인 + 실측 검증, 2026-07-21)**
- 각 팀 블록에서 **상단→하단이 경력·업무 수행능력 순**. 명단 순서 자체가 정보다
  (→ Nurse.seniority_rank 로 모델링, 상세 명단 §5.1과 연결).
- **미드(M) = 저연차 근무** ✅ 실측 확정: 두 달간 미드(M·M/D·M/E) 수행자는 전원
  **팀 내 4~8위(하위권)**, 팀 상위 1~3위는 **미드 0회**. 8월 미드 최다 수행자는
  1팀 막내 한예은(3회). → 구현: "미드는 팀 하위권(저연차)에 우선 배정" 소프트
  (+상위권 배정 금지 여부는 면담 A1에서 확인).
- **팀당 교대 1명이 기본형**: 정확히 1명인 날이 37~63%, 2명도 흔함, **0명은 61일×3교대×3팀
  중 단 1건**. → 팀당 각 교대 **최소 1명 = 하드**, "정확히 1명" = 기본형(목표 인원은 B1 확인).
- **프리셉터 규칙 (사용자 확인, 2026-07-21)**: **각 팀 최고참(1위)이 프리셉터**가 기본
  — 1팀 이지우 · 2팀 오수아 · 3팀 문윤서. **프리셉티(신규)가 있을 때만** 동행 배정이
  발동한다.
  - 실측과 정합: 2팀은 신규가 있어 동행 발생(7월 홍예준 12일 중 9일, 8월 전시은 9일),
    3팀 정현서 8월 나이트 4일 연속 동행(나이트 교육), **1팀은 신규가 없어 동행 없음**.
  - 구현: `preceptor = 팀 1위(기본값, 변경 가능)` + 프리셉티 지정 시 **같은 근무 배정
    소프트 제약**(실측 동행률 ~75%로 100% 강제는 아님 — 강도·기간은 면담 F2 확인).

**아직 확정 안 된 값** *(파트장 면담으로 확인 — docs/INTERVIEW_QUESTIONS.md)*
- ✅ 팀↔근무표 연동 = **A안(팀 고정)** 확정 (§3.1.1)
- 팀별 담당 병실 구성(어느 호실이 어느 팀인지), 교대별 팀별 최소 인원 수치
- 미드(M) 시간대·인원, 신규 기준 개월 수, 개인 신청 월 최대 개수, 공휴일 처리, 주말 정책 등

### 3.1.1 팀(Team) 개념 — ✅ A안(팀 고정) 확정 (2026-07-21)

**결정: (A) 팀은 간호사의 고정 속성.** 근무표는 근무(D/E/N/M/O)만 배정하고 팀은 안 건드린다.

- **데이터 근거**: 실제 7·8월 표에서 **매일 각 교대(D/E/N)를 3팀이 모두 자체 커버**
  (D·E는 31/31일, N은 61일 중 1일만 예외). → 팀 고정 + 각 팀 자체 staffing이 현실.
- Nurse에 `team` 속성(고정). 결정 변수는 `x[간호사, 일, 근무]`만 → **모델 단순**.
- **교대별 팀별 최소 인원** = 하드 제약(각 교대에 팀1·2·3 각각 ≥1, 실측 확인). 값은 튜닝.
- 팀 연속성은 고정 속성이라 **자동 보장**(별도 소프트 제약 불필요).
- **"불가피 시 팀 변경"** 예외: 솔버 결정이 아니라 **파트장이 명단에서 해당 기간 소속을
  수동 변경**하는 방식으로 처리(드문 케이스, 실측 60여 건 중 1건).
- (B안 팀도 솔버가 배정 = 간호사×일×팀 변수 추가는 불필요한 복잡화 → 채택 안 함.)

  마감 후 신청·수정 차단(§7.5.7)

- 피드백/요청 전달(마스터 수신함, §7.5.6-B)
- **내보내기(엑셀 .xlsx / 이미지) — 전 역할 사용 가능**(§7.5.9)
- 3등급 권한(마스터/관리자/일반), 멀티 병동

### 4.2 근무표 작성 규칙 (이론 → 구현 매핑)

|---|-----------|------|----------------|-------------|------|

| T3 | 주 근무 ≤ 6 | 주 6일 이상 근무 금지 | 7일 슬라이딩 윈도우 근무 ≤ 6 (= 7일마다 최소 1 휴무) | 하드 | ✅ 검증됨 |
| T4 | 월 OFF 쿼터 | 그 달 토(SO)+일(주OFF)+공휴일(HO) 갯수만큼 오프 반영 | 간호사별 목표 OFF 수 = 주말+공휴일 수 | 하드/소프트(결정) | ⬜ |
| T5 | OFF 라벨 구분 | 토=SO, 일=주OFF, 공휴일=HO (표시용) | 표시 코드 세분화(연차와 별개) | 표시 | 🟡 |
| T6a | **나이트 블록 ≥ 2** | 단일 N 금지 (실측: 단일 N **0건** — 항상 2연속 이상) | N 블록 길이 ≥ 2 강제 | **하드** | ✅ 실측 검증 |
| T6b | D/E 블록 ≥ 2 (풍당풍당 X) | D/E 고립 단일근무 지양 (실측 월 3~4건 예외) | 고립 D/E 감점 | 강한 소프트 | ✅ 재분류 |
| T7 | 나이트 후 OFF | 마지막 나이트 다음 날 반드시 OFF. **연속 2일+ 야간 후 48시간(≈오프 2개) 휴식**은 복지부 가이드라인 | N 블록 OFF 종료(하드) + 오프 2개(준하드, C3 확인) | 하드(+48h 준하드) | ✅/⚠️ C3 |
| T8 | 연속 나이트 상한 | 연속 나이트 최대 **3** — 실측 + **복지부 가이드라인**과 일치 | 연속 N ≤ 3 | 하드 | ✅ 확정=3 (공식 근거) |
| T9 | 월 나이트 상한 | 한 달 N ≤ 7, 2개월 합 ≤ 15 (병원마다 상이) | 간호사별 월/2개월 N 합 상한 | 하드(파라미터) | ⚠️ 값 확인 |
| T10 | N전담(N KEEP) | 야간 전담 월 야간 **14일(제정)→15일(2023 개정)** 이내 — 복지부 가이드라인 | 전담 간호사 전용 규칙 세트 | 하드(파라미터) | ⚠️ 도입 여부 |
| T11a | 지양 패턴(하드) | E→D 직접, N-OFF-D(NOD) | 전이/2일갭 금지 | **하드** | ✅ 검증(0건) |
| T11b | 지양 패턴(소프트) | E-OFF-D(EOD) | 감점(지양하되 허용) | **소프트** | ✅ 재정의(§4.4) |
| T12 | 임산부·산부 보호 | **근로기준법 §70**: 임산부(임신 중+산후 1년 미만) 야간(22–06) 원칙 금지(본인 동의/청구+장관 인가 시 예외). **§71**: 산후 1년 미만 연장근로 제한(1일 2h·주 6h·연 150h) | 나이트 제외 대상 포함. 예외 운영 여부는 병동 정책(D3) | 하드(법규) | ✅ 법조문 확정 |
| T13 | 경력 분포 | 듀티마다 경력자 고루, 특히 N에 경력자+신규 혼합 | 교대별 경력자 ≥ 1 등 | 소프트→가능시 하드 | ⬜ |

### 4.3 작성 순서 힌트 (사람이 짜는 순서 = 알고리즘 검증용)
1. **N을 규칙성 있게 2개씩 먼저** 배치 (→ 절반 완성)
2. N 뒤 OFF 부여
3. 공휴일·토·일 갯수로 필요한 OFF 수 계산
4. 요청사항(오프날·연차) 최대 반영
5. D·E 채우기

> CP-SAT는 전역 최적화라 이 순서를 그대로 따르진 않지만, 결과 검증·휴리스틱
> 초기해(warm start) 설계에 참고한다. "N이 근무표의 뼈대"라는 우리 접근과 일치.

### 4.4 실제 근무표 검증 결과 (2026 7·8월 대조) — ✅ 데이터 근거 확보

`data/verify_rules.py` 로 실제 근무표에 규칙을 대조한 결과. **현실이 채점한 규칙**이다.

**✅ 100% 지켜짐 → 하드 제약 확정**
| 규칙 | 7월 | 8월 |
|------|-----|-----|
| 나이트 후 D/E/M 금지(T7) | 0건 | 0건 |
| 역회전 E→D 금지 | 0건 | 0건 |
| N-OFF-D 금지(T11) | 0건 | 0건 |
| 주 근무 ≤ 6일(T3) | 0건 | 0건 |
| 연속 근무 ≤ 5일 | 최대 5 | 최대 5 |
| 연속 나이트 ≤ 3(T8) | 최대 3 | 최대 3 |

> **T8 확정**: 자료(블로그)는 "나이트 4회 후 오프"였으나 실제 표는 **연속 나이트 최대 3**.
> → 우리 병동 기준 **연속 나이트 상한 = 3**.

**⚠️ 예외 존재 → 소프트/재검토**
| 규칙 | 7월 | 8월 | 조치 |
|------|-----|-----|------|
| EOD(E-OFF-D) 지양(T11) | 20건 | 14건 | 하드 아님 → 약한 소프트 |
| 고립근무(풍당풍당, T6) | 4건 | 3건 | 강한 소프트(드문 예외 허용) |
| 주 OFF ≥ 2(T2) | 141건 | 70건 | (아래에서 재정의됨) |

**T2 "주 오프 ≥ 2" 재정의** (여러 해석을 실제 표에 대조한 실험 결과):
- 슬라이딩 7일·OFF만 = 211/211 위반(전부) → 완전히 틀린 해석
- 달력주(월~일)·오프+연차 = 68주 중 16주만 <2 (**충족률 약 76~80%**)
- **어떤 해석으로도 위반 0건이 안 됨** → **하드 규칙이 아님**. 실제 표는 나이트 몰린 주에
  오프 1개인 주를 허용(예: 조하은 7월 6~12일 = 6일 근무+오프 1).
- **결론**:
  - 하드(항상 지켜짐): **7일마다 최소 1 휴무**(= 주 근무 ≤6, T3).
  - 소프트(선호): **달력주(월~일) 오프+연차 ≥2** 되도록 목적함수 감점.
  - 근거: 블로그의 "토=SO + 일=주OFF"가 곧 한 주의 오프 2개(주말) → 달력주가 기준.

**나이트 공정성**: 1인 평균 약 5.7~5.8개, 최소~최대 5~7개(전출자 제외) — 실제로 고르게 분배됨.

**T11 지양 패턴 세분화** (E-OFF-D 재검토 결과):
- 블로그가 "지양"으로 묶은 3개 중 실제로는 **하드 2 + 소프트 1**로 갈림.
  - **E→D 직접 = 0건, N-OFF-D = 0건** → **하드**(절대 안 함).
  - **E-OFF-D(EOD) = 20건/14건** → **소프트**(지양하되 불가피 시 허용).
- EOD 실제 빈도: 1인당 월 **0.6~0.8건**, 간호사 절반가량은 **0건**, 전체 오프의 **6~10%**.
- 이유: N-OFF-D는 나이트 후 오프 1개뿐이라 회복 부족(하드), E-OFF-D는 휴식 약 33h로
  덜 심각(소프트).
- **구현**: EOD는 **중간 세기 소프트 감점** — 목표는 실제 표 수준(1인 월 ≤1건)으로 희소하게 유지.

  연속오프 min/max · 주말 통짜(complete weekend) · 선호 반영 · **이월(border) 처리 명시**.
- CP-SAT가 유전알고리즘 대비 ~225배 빠르다는 실험 보고 → 우리 스택 선택 타당.

언론·노조 자료에서도 일관 확인(모두 P1·P2·P3로 이미 커버).

## 5. 데이터 모델 (확장 방향) — 🟡

### 5.1 Nurse (간호사) — 부서장 관리 명단

부서장(파트장)이 관리하는 **상세 명단**. 단순 이름 나열이 아니라 배정·규칙에 필요한
다양한 속성을 담는다. **상세 정보는 관리자·마스터만 열람**(일반 부서원 비공개, §7.5.10).

| 필드 | 설명 | 공개 범위 |
|------|------|-----------|
| `id`, `name`, `empno` | 이름·사번 | 이름은 근무표에 표시(전체), 사번은 관리자 |
| `team` | 소속 팀(1/2/3), 고정 속성(A안) | 관리자 |
| `seniority_rank` | **팀 내 경력·능력 순위**(명단 순서). 미드 배정·경력 분포·표시 순서에 사용 | **관리자 전용** |
| `experience` | 경력(입사일/연차) | **관리자 전용** |
| `is_new` | 신규 여부(입사 N개월 미만) | **관리자 전용** |
| `competency` | 실제 업무 능력·숙련도(부서장 평가) | **관리자 전용(민감)** |
| `night_eligible` | 나이트 가능 여부(신규·임신 시 false) | 관리자 |
| `employment_type` | 고용형태(정규·파트타임 등) | **관리자 전용** |
| `charge_capable` | 차지 가능 여부 | 관리자 |
| `preceptor_of` | 프리셉티(교육 대상) 연결 | 관리자 |
| `skills` | 특수 처치·장비 자격 | 관리자 |
| `note` | 비고 | **관리자 전용** |

- 부서장은 이 명단을 **추가·수정**할 수 있다(간호사 명단 관리 화면).
- 배정 규칙(신규·임신 나이트 제외, 경력 분포, 차지 등)이 이 속성들을 사용한다.
- `competency`처럼 민감한 평가 항목은 특히 **부서장 외 노출 금지**.

### 5.2 WardConfig (병동 설정)
- 요일별 **교대별·팀별** 최소 인원: 평일 / 주말 / 공휴일 구분
- **적정(목표) 인원**(선택): 최소 인원(하드)과 별도로 목표 인원을 두고 부족분 감점(INRC S1 방식)
- 회전 규칙 매트릭스(6절 참고)
- 연속 근무일 상한 / 연속 나이트 상한
- 간호사별 최소 오프
- 팀 목록(3개) 및 팀당 인원(약 7~8명)

### 5.3 MonthContext (월 컨텍스트)
- `year`, `month` → 일수·요일·주말·공휴일 자동 산출
- 공휴일 소스: 수동 입력 vs 자동 (⬜ 결정 대기)

### 5.4 Carry-over (전월 이월)
- 간호사별 전월 말일 마지막 근무 시퀀스(예: 마지막 1–3일)
- 용도: 월초 연속근무·연속나이트·경계 회전 제약 계산

### 5.5 PreAssigned (사전 배정)
- `{nurse_id, day, code}` — 연차·공가 등 하드 고정

### 5.6 Requests (개인 신청 · 원티드)
- `{nurse_id, start_day, end_day, shift: D|E|N|OFF, reason}` — 소프트 반영
- **근무 종류 4가지 신청 가능**: 데이·이브닝·나이트·오프.
- **오프 최우선 반영** — 오프 신청을 최상위 소프트 가중치로. D/E/N 원티드는 낮은 가중치.
  신청 화면 안내문구: *"오프가 최우선으로 반영됩니다. 데이·이브닝·나이트 원티드는
  반영되지 않을 수 있습니다."*
- **기간 신청**: 하루 또는 **연속 여러 날(시작일~종료일)** 선택.
- **내 신청 현황은 달력(캘린더) 형식**으로 표시(색상=근무 종류).
- 신청 기간(윈도우)은 파트장이 통제(§7.5.7). 월 최대 신청 개수 제한 (⬜ 값 결정 대기).

## 6. 제약조건 상세 — 🟡

### 6.1 하드 제약 (반드시 준수)
1. 각 간호사는 하루에 근무/휴무 중 정확히 하나 배정
2. 요일별·교대별·**팀별** 최소 인원 충족 (각 교대에 팀1/2/3 각각 최소 인원)
3. **역회전 금지 매트릭스** (전날→다음날 전이 금지)
4. 연속 근무일 상한 (전월 이월 포함)
5. 연속 나이트 상한 (전월 이월 포함)
6. 신규·임신 간호사 나이트 배정 금지
7. 사전 휴무(연차 등) 고정
8. 간호사별 최소 오프
9. *(대원칙에서 추가되는 항목 반영)*

### 6.2 회전 매트릭스 — ✅ 실데이터 검증 반영
근무 순서 랭크: `D(1) → M(2) → E(3) → N(4)`. 실제 7·8월 표의 연속 근무 전이 빈도로
"절대 금지(하드) / 강한 지양(소프트) / 허용"을 구분했다.

| 전날↓ \ 다음날→ | D | M | E | N | O | 근거(실측 건수) |
|---|---|---|---|---|---|---|
| **D** | 허용 | 허용 | 허용 | 허용 | 허용 | D→D184·M4·E42·N18 |
| **M** | ⚠️소프트 | 허용 | 허용 | 허용 | 허용 | M→D **1건**(강한 지양) |
| **E** | ⛔하드 | ⚠️소프트 | 허용 | 허용 | 허용 | E→D **0건**(금지)·E→M 1건(지양) |
| **N** | ⛔하드 | ⛔하드 | ⛔하드 | 허용 | 허용 | N→D/E/M **모두 0건**(금지) |
| **O** | 허용 | 허용 | 허용 | 허용 | 허용 | — |

- **⛔ 하드(절대 금지)**: N→D, N→E, N→M, E→D (실측 0건). → 대원칙 P1·P3.
- **⚠️ 소프트(강한 지양)**: M→D, E→M (실측 각 1건). 절대 금지가 아니라 감점 대상.
- **허용**: D→모든 근무, E→E/N, M→나머지, 순방향(D→M→E→N) 전반.
- 별도 2일갭 패턴: N-OFF-D=하드(0건), E-OFF-D=소프트(20/14건, §4.4).

## 7.5 운영/배포 아키텍처 — ✅ 방향 확정 (비용 최소화)

### 7.5.1 사용자 등급 (RBAC)
| 역할 | 대상 | 권한 |
|------|------|------|
| **마스터** | 나 | 전체 관리 · 병동/사용자 관리 · 모든 기능 · **피드백 수신함** |
| **관리자** | 파트장 | 근무표 생성·수정·확정, 오프신청 승인/반려, **오프 신청 기간 설정·통제**, **간호사 상세 명단 관리(추가·수정·열람)**, **피드백 전송** |
| **일반** | 부서원 | 근무표 조회, **원티드 오프 신청**(신청 기간 내), 본인 통계 확인, **내보내기(엑셀·이미지)**, **피드백 전송** (상세 명단 열람 불가) |

- 모든 역할은 마스터에게 **피드백/요청 메시지**를 남길 수 있다(7.5.6-B).
- **내보내기(엑셀·이미지)는 전 역할 사용 가능**(부서원 포함, §7.5.9).

### 7.5.2 배포 스택 (사실상 $0)
```
[브라우저] → [Cloudflare(무료, 도메인·CDN, 선택)]
           → [FastAPI + OR-Tools 컨테이너 : Google Cloud Run(scale-to-zero)]
           → [Supabase(무료): 인증 + Postgres DB]
```
| 구성 | 서비스 | 비용 | 이유 |
|------|--------|------|------|
| 인증 + DB | **Supabase** 무료 티어 | $0 | 회원가입·로그인·3등급 권한 + 데이터 저장을 한 번에 |

> **현재 구현 상태(개발 단계)**: 자체 인증(`app/auth.py` — JWT+SQLite+scrypt, 최초 가입자=마스터,
> 마스터가 역할 승격)이 이미 동작한다. 배포 시 Supabase Auth로 교체하거나 자체 인증을
> 그대로 쓸지 Phase 5에서 결정 — auth 모듈에 격리돼 있어 어느 쪽이든 교체 비용이 작다.
| 백엔드 엔진 | **Google Cloud Run** | ~$0 | scale-to-zero, 무료 한도 넉넉, OR-Tools 컨테이너 실행 가능 |
| 도메인·보안 | **Cloudflare** 무료 | $0 | (선택) 주소·CDN. 처음엔 생략 가능 |

- **더 쉬운 대안**: 백엔드를 **Render 무료 티어**로(git 연결 배포, 설정 최소). 콜드스타트가 김.
- ⚠️ **OR-Tools는 Cloudflare Workers/엣지에서 실행 불가** → 반드시 컨테이너 호스트 필요.

### 7.5.3 무료 티어 유의점
- Cloud Run: 유휴 후 첫 요청 **콜드 스타트(수초)** — 근무표는 자주 안 만드니 무방.
- Supabase: 무료 프로젝트 **1주 미사용 시 일시정지**(재사용 시 자동 복구).
- 무료 정책 변동 가능 → 주기적 확인.

### 7.5.4 데이터 모델(운영) 추가 필요
- `User`(이메일, 역할, 소속 병동), `Ward`(병동), `Schedule`(월별 근무표),
  `OffRequest`(원티드 오프 신청: 신청자·날짜·상태[대기/승인/반려])
- `RequestWindow`(병동·대상월·신청 시작일·마감일·상태[열림/마감]) — 파트장이 설정, 신청 기간 통제(7.5.7)
- `Feedback`(작성자·병동·내용·작성시각·상태[신규/읽음/처리]) — 마스터 수신함용(7.5.6-B)
- 인증·권한은 Supabase Auth + Postgres RLS(행 수준 보안)로 역할별 접근 제어.

### 7.5.5 확장성 (Scalability) — 소규모 → 병원 전체

**목표 규모**: 병상 약 370, 병동 약 10개(현재 51·61·62·71·72·82·92 + 추후 오픈),
간호사 약 250명 + 파트장·마스터 ≈ **총 300명**. 사용 패턴은 근무표 생성 **병동당 월 1회**,
부서원 조회·오프신청 **월 수회** → **트래픽·연산량이 매우 낮은 앱**.

**핵심 결론**: 병원 전체로 확장해도 **재구축 불필요**. 대부분 **요금제 상향**으로 해결된다.

| 항목 | 소규모(구축) | 병원 전체 | 변경 |
|------|-------------|-----------|------|
| 기본 구조(Supabase+Cloud Run) | 그대로 | 그대로 | ❌ 재구축 없음 |
| Cloud Run 연산 | 무료 한도 내 | 여전히 무료 한도 내 | ❌ 거의 그대로 |
| DB 용량 | 수 MB | 수백 MB(수년치) | ❌ 여유 |
| 요금제 | 전부 무료 | Supabase만 Pro(~$25/월) | ✅ 신뢰성(백업·무정지)용 |
| 예상 비용 | ~$0 | **월 약 $30~40** | 저렴 |

**지금부터 반드시 설계할 것 — 멀티테넌시(멀티 병동)**:
- `Ward` 테이블 + 모든 데이터(User/Schedule/OffRequest)에 **병동 소속(ward_id)** 부여.
- 병동 오픈 = **행(row) 추가**만으로 확장(코드 변경 없음).
- **RLS(행 수준 보안)**: 파트장은 자기 병동만, 부서원은 자기 병동 근무표만 접근하도록 격리.
- 마스터는 전 병동 접근.

> 요약: **무료로 시작 → 커지면 요금제만 상향**. 단, "여러 병동"을 처음부터 전제로 설계해
> 두면 확장 시 데이터만 추가하면 된다(재작업 없음). 스택(Cloud Run/Supabase)을 고른
> 이유가 바로 이 **작게 시작해 그대로 키우기** 때문.

### 7.5.6 업데이트 반영 & 피드백 (운영 요구)

**A. 업데이트가 모든 사용자에게 반영 — 웹 앱이라 기본 해결**
- 웹 앱은 **서버 한 곳에서 제공** → 마스터가 새 버전을 배포하면 사용자는
  **다음 접속(새로고침) 때 자동으로 최신 버전**을 받는다(설치형 앱처럼 개별 업데이트 불필요).
- **자동 배포(CI/CD)**: GitHub에 push → Cloud Run/Render가 **자동 재빌드·배포**.
  마스터는 코드만 올리면 반영 끝.
- **초반 잦은 수정 대비**:
  - **정적 자원 캐시 무효화**(버전 해시) → 브라우저가 옛 JS/CSS를 물고 있지 않게.
  - **열려 있는 화면 알림**: "새 버전이 있습니다 · 새로고침" 안내(선택).
  - **DB 마이그레이션**: 데이터 구조 변경 시 기존 데이터 보존하며 스키마 갱신
    (초반엔 변경이 잦으므로 마이그레이션 도구/절차를 처음부터 마련).

**B. 피드백/메시지 기능 — 마스터에게 요청 전달**
- 모든 사용자가 앱에서 **요청/메시지**를 남기면:
  1. **마스터 관리자 계정의 수신함(대시보드)** 에 표시(상태: 신규/읽음/처리) — 기본.
  2. **(선택) 마스터 이메일로 전송** — 즉시 인지용.
- 구현(비용 최소):
  - 저장은 `Feedback` 테이블(무료 DB) → 대시보드 표시.
  - 이메일은 **무료 티어 발송 서비스**(예: Resend 무료, 월 다수 무료) 또는 Supabase 연동.
    이메일 없이 대시보드만으로도 동작(이메일은 부가).

### 7.5.7 오프 신청 기간(윈도우) 통제 — 부서장 관리

- **부서장(파트장)이 병동별로** 오프 신청 기간을 설정한다: 대상 월, **신청 시작일·마감일**.
- **마감 후 부서원의 신청·수정 차단**. 신청 화면에서 아래 경고 문구 표시:
  > **"신청 기한이 만료되었습니다. 추가 수정 필요 시 부서장에게 직접 문의하세요."**
- 기간 상태(열림/마감)는 파트장이 수동으로 조기 마감·재개도 가능.
- 병동마다 기간이 독립적(멀티테넌시) — 61병동과 62병동의 신청 기간이 서로 다를 수 있음.
- UI: 신청 기간 중에는 남은 기간·마감일 안내, 마감 시 위 경고로 대체하고 제출 버튼 비활성화.

### 7.5.8 반응형 (모바일 + 데스크탑)

- **하나의 반응형 웹**으로 두 기기를 모두 지원(별도 앱 설치 불필요).
- **부서원(폰 위주)**: 근무표 조회·본인 근무 확인·오프 신청·피드백 — 모바일 최적화(세로 스크롤,
  큰 터치 영역, 내 근무만 강조 보기).
- **파트장(데스크탑 위주)**: 근무표 생성·편집·승인 등 넓은 화면이 필요한 작업.
- 근무표 그리드는 좁은 화면에서 **가로 스크롤 + 이름 고정열**, 또는 **본인/팀 중심 축약 보기** 제공.

### 7.5.9 내보내기 (엑셀 · 이미지) — 전 역할

- **모든 역할(부서원 포함)** 이 근무표를 내보낼 수 있다.
- **형식 2가지**:
  - **엑셀(.xlsx)**: 병동 양식대로 표 형태. 인쇄·공유·보관용. (서버에서 openpyxl 등으로 생성)
  - **이미지(PNG/JPG)**: 근무표 화면을 이미지로. **폰에서 카톡 등으로 바로 공유**하기 좋음.
    (좁은 화면에선 "본인/팀 축약 보기"도 이미지로 내보내기 가능)
- 범위 선택: 전체 근무표 / 본인 근무만 / 특정 팀 (부서원은 본인·팀 중심이 유용).
- 개인정보 유의: 외부 공유 이미지엔 필요한 범위만 담기도록 옵션 제공.

### 7.5.10 간호사 상세 명단 & 접근 제한

- **부서장(파트장)이 병동 간호사 명단을 관리**(추가·수정): 팀·경력·업무능력·나이트 가능·
  고용형태·차지·프리셉터·스킬·비고 등 상세 속성(§5.1).
- **일반 부서원은 상세 명단을 볼 수 없다.** 부서원에게 보이는 것은:
  - 근무표의 **이름**(누가 언제 근무인지)과 **본인의 정보**뿐.
  - 경력·업무능력(competency)·고용형태·비고 등 **민감 속성은 관리자·마스터 전용**.
- 구현: Postgres **RLS(행 수준 보안)** + 필드 수준 접근 제어로 역할별 노출 범위를 강제.
  민감 필드는 별도 테이블/뷰로 분리해 일반 사용자 API 응답에서 제외.
