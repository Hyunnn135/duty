# 작업 지시서: 관리자용 데이터 백업 내려받기 + 미백업 경고

- 발행일: 2026-08-20 / 근거 결정: D-15(B안 승인)
- 티어: **T3(중대)** — 인증·권한 + 개인정보 반출 + DB 스키마 신설이 동시 해당
- 마스터 계획 승인: **승인됨 (2026-08-20)** — ①권한 계정 1인 지정 ②전체 데이터 반출 ③단계적 경고

## 핵심 위험 (설계 근거)
`role=="master"`는 **병동마다 부여**된다(병동 개설자=그 병동 마스터). 역할만으로 권한을
판정하면 타 병동 개설자가 전 병동 간호사 실명·사번이 든 DB를 반출할 수 있다.
→ **환경변수 allowlist + role==master 동시 충족**일 때만 허용한다.

## 목표
허가된 단일 계정만 버튼 한 번으로 일관성 있는 전체 백업을 내려받을 수 있고,
마지막 백업 후 30일이 지나면 백업을 실제로 할 때까지 경고가 반복 노출된다.

## 범위 — 포함
1. `GET /api/admin/backup` — 인증 필수, 허가 계정만 200(ZIP), 그 외 403(무인증 401)
2. 일관성 있는 스냅샷: `VACUUM INTO` (폴백 `Connection.backup()`). **파일 직접 복사 금지**
   (운영 DB는 WAL 모드라 -wal 미반영/손상 위험)
3. 권한: 환경변수 `DUTY_BACKUP_OWNER`(사번/이메일, 콤마 구분) ∧ role==master.
   admin·staff 불허. **미설정이면 전원 403**(기본 개방 금지)
4. `backup_log` 테이블 신설(actor, ward, created_at, byte_size, status) +
   `GET /api/admin/backup/status` → {last_backup_at, days_since, level: ok|warn|critical}
5. 프런트: 설정 영역 "💾 백업 내려받기" 버튼 + 경고 팝업/고정 배너, 허가 계정에만 노출
   (`data-admin` 재사용 금지 — 별도 플래그)
6. 자동 테스트(권한 경계·일관성·상태 계산·노출 제어). 데이터는 가명만(교훈 L-1)
7. 문서: USER_GUIDE(백업 방법·보관 주의), DEPLOY(환경변수·복구 절차) — 교훈 L-5

## 산출물 구성 (ZIP 1개)
- `duty.db` — 복구 정본
- `tables/{테이블}.csv` — 7개 전량, **UTF-8 BOM**(엑셀 한글 깨짐 방지)
- `README.txt` — 한국어: 무엇인지 / 백업 시각(KST) / 복구 요청 방법 / 개인정보 포함, 공유 금지
- 임시 파일은 `finally`에서 반드시 삭제(개인정보 잔존 금지)

## 경고 규칙 (마스터 승인)
- 0~29일: 경고 없음, 설정에 "마지막 백업: N일 전"만 표시
- 30일↑: 로그인 후 첫 진입 시 팝업 [지금 백업하기]/[오늘은 나중에].
  "나중에"는 **KST 당일 자정까지만** 유효 → 다음 날 재노출
- 45일↑: 팝업 + **닫을 수 없는 상단 고정 배너**, 백업 성공 시에만 사라짐
- 경과일 판정은 **서버가 계산**(저장 UTC / 판정·표시 KST — 교훈 L-4)

## 범위 — 제외
복원(업로드) 기능, 자동·정기 백업, 외부 스토리지 업로드, 메일 발송,
병동별 부분 백업, ZIP 암호화, 기존 엑셀 내보내기 변경, 인프라 변경

## 수용 기준
1. 허가 계정 → 200+ZIP / 미허가 master·admin·staff → 403 / 무인증 → 401.
   거부 응답 본문에 실명·사번 미포함. `DUTY_BACKUP_OWNER` 미설정 시 전원 403
2. 백업 직전 커밋된 행이 ZIP의 duty.db와 해당 CSV **양쪽**에 존재. 백업 중·후에도
   원본 DB 읽기·쓰기가 계속 성공
3. ZIP에 duty.db 1개 + 7개 CSV + README.txt. CSV 첫 3바이트가 UTF-8 BOM,
   한글 헤더 정상. 요청 종료 후 서버에 백업 임시 파일 잔존 0
4. 성공 1회당 backup_log 행 1개(status='ok', byte_size>0). 403 요청은 행 미추가
5. KST 기준 경과 29일→ok / 30일→warn / 45일→critical / 이력 0건→critical.
   UTC로 계산하면 달라지는 경계 시각에서도 KST 결과가 나옴
6. (E2E) warn에서 팝업 표시, "오늘은 나중에" 후 같은 날 재노출 안 됨·날짜 바뀌면 재노출.
   critical에서 닫기 불가 배너 표시, 백업 성공 후 배너·팝업 소멸.
   staff·admin 로그인 시 버튼·팝업·배너·상태가 DOM에 렌더링되지 않음
7. USER_GUIDE·DEPLOY 문서 갱신, 전체 테스트·E2E 초록, 기존 테스트 완화 0,
   신규 테스트에 실명·실제 사번 없음

## 완료 조건
품질부 독립 검증(구현 역산 금지) + **검수부 3관점**(①권한·인증 우회 ②개인정보 반출·잔여
③데이터 일관성·복구 가능성) + 판별력 입증(역대조/표적 뮤테이션, 실패 로그 첨부) +
전체 테스트·E2E 통과 + 마스터 배포 승인 → PR → CI → 병합 → 배포 확인 + 교훈 대장 기록

## 관련 교훈
L-1(테스트 데이터 가명만) · L-4(저장 UTC/판정 KST) · L-5(동작 규칙 변경 시 문서 동시 갱신)

# 보완 지시 (2026-08-20, 검수부 3관점 결과 반영 — 운영자 승인)

검수부 ①(권한 우회)·②(개인정보 반출)가 **실제 침투를 재현**했다. 아래는 배포 전 필수 수정.

## 필수 1 — 권한 판정을 불변 내부 식별자(uid)로 전환 [치명·운영자 지시]

**문제(재현됨)**
- **선점**: 판정 기준이 "문자열"이라 `DUTY_BACKUP_OWNER` 값이 아직 어느 계정에도 묶이지
  않았으면 누구나 새 병동을 열어 master가 된 뒤 그 사번을 등록해 전체 DB를 반출할 수 있다.
  배포 문서가 안내하는 "환경변수 먼저 설정" 순서에서 이 창이 기본으로 열린다.
- **유니코드 접힘**: 이메일은 `lower()` 저장인데 비교는 `upper()`. 점 없는 ı(U+0131) 등을
  쓴 다른 이메일이 같은 대문자열로 접혀 allowlist를 통과한다.

**요구사항**
1. 판정은 `users.id`(불변 내부 식별자) 기준으로 한다. 환경변수는 `DUTY_BACKUP_OWNER_UID`
   (콤마 구분 정수). **문자열 사번·이메일 기반 판정은 제거**한다(하위 호환 두지 말 것 —
   그 자체가 취약점이다).
2. 미설정·빈 값·정수가 아닌 값 → **전원 403**(fail-open 금지) 유지.
3. `role=="master"` 결합 조건은 유지하되, 이것이 실질 방어가 아님을 코드 주석·문서에
   정확히 기술한다(누구나 새 병동 개설로 master가 된다).
4. 운영자가 **자기 uid를 확인할 수 있는 경로**를 제공한다(예: `/api/auth/me` 응답에 uid
   포함 + 설정 화면 표시). 비개발자가 서버 접속 없이 확인할 수 있어야 한다.
5. `docs/DEPLOY.md` §7.6과 Railway 절차를 새 방식으로 다시 쓴다: **가입 먼저 → uid 확인
   → 환경변수 설정** 순서를 명시하고, 이메일 지정 안내는 삭제한다.

## 필수 2 — 백업 산출물에서 자격증명 제거 [높음]

**문제(재현됨)**: `users.csv`에 전 계정 `pw_hash`·`salt`, `ward_invites.csv`에 **전 병동의
유효한 초대 코드**가 평문으로 나간다. 검수부가 그 코드로 실제 가입에 성공했다.
복구 정본은 `duty.db`이므로 **CSV의 이 값들은 이득 0, 위험만 있다.**

**요구사항**
1. CSV 생성 시 `users.pw_hash`·`users.salt`·`ward_invites.code` 값을 `(생략)`으로 마스킹한다.
   `duty.db` 정본은 그대로 둔다(복구 능력 유지).
2. 새 테이블이 추가돼도 민감 값이 자동으로 새지 않도록, 마스킹 대상을
   `테이블.컬럼` 목록 상수로 명시하고 주석에 근거를 남긴다.

## 필수 3 — 중단된 백업이 "성공"으로 기록되는 문제 [중간]

**문제(재현됨)**: 응답 전송 전에 `_log()`를 호출해, 다운로드가 끊기거나 사용자가 저장을
취소해도 `status='ok'`가 남고 경고가 30일간 꺼진다. 파일은 없는데 시스템은 있다고 믿는다.

**요구사항**: 성공 이력이 **실제로 파일이 전달된 뒤** 남도록 고친다. 구현 방식(응답 완료
후 기록 / 프런트 확정 신호 등)은 개발부가 판단하되, 근거를 보고하라.

1. 백업 응답에 `Cache-Control: no-store` 추가(`/backup/status`도 권장) — 전체 DB 사본이
   브라우저 캐시에 남는 것 방지.
2. 거부(403) 시도를 `backup_log`에 `status='denied'`로 남긴다(개인정보 없이 uid·시각만).
   현재는 침입 시도를 탐지할 수단이 전혀 없다.
3. `.gitignore`에 `*.zip` 추가 — 저장소 폴더에 백업을 받으면 개인정보가 커밋될 수 있다.

   - "OneDrive·iCloud가 켜진 폴더(바탕화면·문서·다운로드)에 두지 마세요 — 자동으로

# 보완 지시 2차 — 운영자 결정 D-19·D-20 반영 (2026-08-20)

검수부 2차 재검수(3관점)에서 **높음 6 · 중간 8 · 낮음 9** 가 재현 근거와 함께 제출됐고,
그중 권한 설계와 개인정보 전달은 운영자 전결로 처리됐다. **아래가 현행 수용 기준이며,
위 본문 중 충돌하는 조항(범위 3, 수용 기준 1, 필수 1)은 이 절이 대체한다.**

## D-19 — 백업 권한을 "계정 번호"가 아니라 "계정 자체"에 붙인다

폐기 근거(검수부 ① 실측 재현): `users.id`는 `AUTOINCREMENT`라 가입 순서대로 1,2,3…
부여된다. 값을 직접 고를 수는 없어도 **먼저 가입하면 원하는 낮은 번호를 차지**할 수
있고, 특히 **DB가 초기화되면 번호가 1부터 다시 시작해 그 뒤 첫 가입자가 백업 권한을
상속**한다(배포자 실수 없이도 성립). 공격자 계정이 200 + 전체 DB ZIP 반출에 성공했다.

현행 기준:
1. 권한은 `users.backup_owner` 플래그(DB)에 저장한다.
   `DUTY_BACKUP_OWNER`·`DUTY_BACKUP_OWNER_UID`는 **완전히 제거**한다 —
   설정해도 아무 효과가 없어야 한다(하위 호환 한 줄이 곧 취약점이다).
2. `POST /api/admin/backup/claim {code}` — `DUTY_BACKUP_CLAIM_CODE`와 일치하면
   그 계정의 플래그가 선다. 비교는 `hmac.compare_digest`.
3. 코드 미설정·빈 값·**8자 미만이면 claim 기능 자체가 비활성**(전원 거부, fail-closed).
4. `role=="master"` 계정만 claim 가능.
5. 실패 시도는 제한·잠금하고 `denied`로 남긴다(uid별 1일 1행 합치기).
6. **핵심 수용 기준**: 빈 DB에 공격자가 첫 가입자(uid 1, master)가 되어도 백업 403.
   플래그가 없으므로 코드를 모르면 반출할 수 없다. **이것이 이 전환의 유일한 존재 이유다.**
7. DB 초기화 시 권한도 사라진다 — 결함이 아니라 설계 의도다. 복구 절차에 재등록을 명시한다.

## D-20 — 복구 시 백업 ZIP은 운영자가 직접 업로드한다

폐기 근거(검수부 ③): USER_GUIDE는 모든 전달 수단(메신저·메일·클라우드)을 금지하는데
DEPLOY는 "받은 ZIP에서 꺼낸다"고 해, **실행하려면 규정을 어겨야 하는 절차**였다.
ZIP에는 전 병동 실명·사번·피드백 원문이 들어 있다.

현행 기준: 파일을 제3자에게 넘기지 않는다. 운영자 본인이 자기 컴퓨터에서 서버로
직접 올린다. 금지 문구는 그대로 유지되며 — 전달 수단을 고르는 대신 **전달 자체를 없앴다.**

## 품질부 3차에서 추가된 수용 기준 (Q-1·Q-2·Q-3·Q-4)

- **부여 감사**: claim 성공 시 `status='granted'` 1행. level 판정에 세지 않는다.
- **권한 회수**: `POST /api/admin/backup/revoke {code}` — 코드 일치 시 **모든 계정의
  플래그를 0으로** 되돌린다. 코드 유출 상황에서 "누가 몰래 등록했는지 모르는 상태"를
  한 번에 정리하는 것이 목적이다. 이후 정당한 운영자가 재등록한다. `status='revoked'` 기록.
- **잠금**: IP 축을 제거하고 **계정 단위로만** 건다(프록시 뒤에서는 IP 축이 사실상 전역
  잠금이 되어 정상 운영자가 막힌다). 카운터는 **DB에 영속화**해 재시작해도 유지한다.
  IP는 저장하지 않는다 — 백업 ZIP으로 실려 나가 교훈 L-1에 걸린다.
- **미설정 기간 기록**: 코드 미설정 상태의 claim 시도도 `denied`로 남긴다.

## E2E 게이트 (검수부 ③ P-1 해소)

수용 기준 6이 "E2E 통과"를 요구하는데 저장소에 하니스가 없어, 높음 결함 3건이 전부
그 사각지대에서 나왔다. 품질부가 `tests/e2e/` 에 재실행 가능한 하니스를 신설했다
(`bash tests/e2e/run_backup_e2e.sh`). 화면을 바꾸는 수정 후에는 반드시 실행한다.
