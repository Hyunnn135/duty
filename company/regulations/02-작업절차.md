# 제2장 — 작업 절차 규정 (파이프라인과 위험 티어)

## 1. 위험 티어 분류 — 모든 작업은 착수 전에 티어를 정한다

티어 판정은 사무국(또는 기획부)이 하되, 판정 근거를 지시서에 남긴다.
애매하면 **한 단계 높은 티어**를 적용한다.

### T1 — 경미 (검수 생략 가능)
- 대상: 오타·문구 수정, 주석·문서, 내부 스크립트, 스타일 미세 조정
- 절차: 구현 → 관련 테스트만 실행 → 병합. 검수부 생략.
- 근거: 위험한 20%만 강하게 게이트해도 리뷰 효과의 대부분(~69%)을 얻는다.
  모든 것을 동일 강도로 검토하면 러버스탬프 아니면 병목이 된다.

### T2 — 일반 (기본값)
- 대상: 일반 기능 추가·수정, UI 변경, 성능 개선
- 절차: 지시서 → 마스터 계획 승인 → 구현 → 품질부 테스트 → 전체 스위트 →
  E2E → 병합 → 배포 확인
- 검수부는 사무국 판단으로 1명 소집 가능

### T3 — 중대 (전 관문 필수)
- 대상: **인증·로그인, 개인정보(간호사 실명·사번 등), DB 스키마·마이그레이션,
  결제·과금, 스케줄링 핵심 알고리즘(근무 규칙), 배포 구성 변경**
- 절차: T2 전체 + 검수부 2~3관점 소집 + (해당 시) 디자인부 + 배포 후 운영부
  확인 + 마스터 배포 승인 명시적으로 획득
- T3에서 발견된 결함과 해결은 반드시 교훈 대장에 기록

## 2. 표준 파이프라인 (T2 기준)

```
[마스터 요구]
   ↓ 기획부: 인터뷰·구체화
[작업 지시서]  ← 완료 정의·수용 기준·티어 포함
   ↓ 마스터 승인 (승인 게이트 ①)
[개발부: 구현]        [품질부: 지시서만 보고 테스트 설계]  ← 병렬, 컨텍스트 분리
   ↓                     ↓
[품질부: 테스트 실행 + E2E]
   ↓ 실패 시 → 개발부 재작업 (실패 로그 첨부 — 말이 아닌 실행 근거로 피드백)
[검수부: 결함 탐색 보고]  (T2는 선택, T3는 필수)
   ↓ 결함 반영
[전체 테스트 + CI]  ← 병합 게이트 (통과 못 하면 병합 불가)
   ↓ 사무국: 통합 보고서 작성
[마스터 배포 승인 (승인 게이트 ②)] → 병합·배포 → 운영부 확인
   ↓
[교훈 대장 기록]
```

## 3. 작업 지시서 표준 양식

모든 T2 이상 작업은 착수 전 아래 양식의 지시서를 만든다.
(근거: 다중 에이전트 실패의 42%가 명세 불량 — MAST)

```markdown
# 지시서: <제목>
- 발행일 / 티어: T1·T2·T3 (판정 근거 한 줄)
- 배경: 마스터의 요구 원문 요약
- 목표: 한 문장
- 범위: 포함하는 것 / 명시적으로 제외하는 것
- 수용 기준: 검증 가능한 문장으로 3~7개
  (예: "사번 중복 가입 시 409와 한국어 안내가 표시된다")
- 완료 조건: 테스트 통과 + E2E 확인 + (T3) 검수부 보고 반영
- 마스터 승인: [ ] 승인일시
```

## 4. 진행 중 규칙

1. **모호하면 멈추고 묻는다.** 지시서와 다른 상황을 만나면 임의로 해석해 진행하지
   말고 사무국에 보고한다(요구사항 되묻기 프로토콜 — ChatDev의 검증된 관행).
   단, 마스터 부재 시 되돌리기 쉬운 선택은 기본값을 택하고 보고서에 명시한다.
2. **반복 상한.** 같은 오류를 3회 수정 시도해 실패하면 접근을 바꾸거나 사무국에
   에스컬레이션한다. 무한 수정 루프 금지(정지 조건).
3. **병렬 작업 조건.** 서로 다른 파일·모듈을 다루는 **독립 작업만** 병렬화한다.
   같은 모듈의 연쇄 수정은 단일 세션이 수행한다(순차 의존 작업의 병렬화는
   오류를 증폭 — 상세 근거는 제6장).
4. **완료 보고의 정직성.** 테스트가 실패하면 실패했다고 보고한다. 일부만 했으면
   일부만 했다고 보고한다. "다 됐다"는 조기 보고는 중대한 규정 위반이다.
