# 제6장 — 비용 규정 (토큰·시간의 경제)

> 실측 근거: 멀티 에이전트는 단일 채팅 대비 **약 15배** 토큰을 쓴다(Anthropic).
> 스텝 수가 늘수록 비용은 비선형으로 커지고, 폭주 시 수십 배까지 간다.
> 반면 위험한 20%만 강하게 게이트해도 검증 효과의 대부분을 얻는다.

## 1. 병렬화(다중 에이전트) 사용 조건

1. 병렬 에이전트는 다음 경우에만 소집한다:
   - **조사·설계**: 서로 다른 각도의 탐색이 가치를 만드는 작업 (예: 3관점 리서치)
   - **독립 작업**: 서로 다른 파일·모듈을 건드리는 작업들의 동시 진행
   - **검수**: 서로 다른 관점의 결함 탐색 (T3)
2. 다음 경우 병렬화를 금지한다:
   - 같은 모듈의 순차 수정(앞 결과가 뒤 작업의 입력이 되는 것)
   - "빨리 끝내려고" 같은 일을 여러 명에게 시키는 것 (오류 증폭 + 낭비)
3. 에이전트·호출 수를 늘리는 결정은 "늘리면 좋겠지"가 아니라 **필요 근거**
   (독립성, 관점 다양성)를 말할 수 있을 때만 한다. 호출 수와 품질은 비례하지
   않고 일정 지점부터 하락한다(비단조 — arXiv:2403.02419).

## 2. 검수 강도 차등 (위험 티어 연동)

| 티어 | 검수 비용 |
|---|---|
| T1 | 검수 생략, 관련 테스트만 |
| T2 | 전체 테스트 + E2E, 검수부 선택적 1명 |
| T3 | 전체 관문 + 검수부 2~3관점 |

## 3. 모델 티어

1. 요약·분류·문구 다듬기·1차 트리아지 등 저위험 단계는 저비용 모델로 다운티어
   할 수 있다.
2. 핵심 구현·보안 검수·최종 통합은 기본(고성능) 모델을 유지한다.

## 4. 반복 작업의 강등 (LLM → 코드)

1. 같은 절차가 3회 이상 반복되면, LLM 판단을 스크립트·cron·결정적 검증으로
   굳히는 것을 검토한다. (근거: LLM은 실행마다 성과 분산이 커서, 반복 자동화의
   사업 리스크는 평균이 아니라 최악 실행이 결정한다 — Vending-Bench)
2. 예: CI 상태 확인, 정기 서버 점검, 백업 확인 → 스크립트 + 예약 실행으로.

## 5. 예산 감각

1. 사무국은 대규모 작업(장시간 병렬·대량 조사) 착수 전에 대략의 규모(에이전트
   수·예상 시간)를 마스터에게 알린다.
2. 구독 한도를 초과할 대형 작업은 착수 전 마스터 승인(전결 1호 '돈'의 연장).
3. 같은 결과를 더 적은 호출로 얻는 방법(캐시, 이전 산출물 재사용, 문서화된
   교훈 참조)을 항상 먼저 검토한다.
