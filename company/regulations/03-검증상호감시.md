# 제3장 — 검증·상호감시 규정

## 1. 승인 권한의 배치 (불변)

1. **어떤 AI 에이전트도 '승인' 권한을 갖지 않는다.**
   - 근거 1: LLM은 같은 계열 모델의 산출물을 체계적으로 과대평가한다
     (자기선호 편향 10~25%, arXiv:2410.21819).
   - 근거 2: AI 코드에 대한 리뷰 승인은 시간이 갈수록 형식화된다
     (승인율 +14.5%p, 코멘트 -22% 실측).
2. 병합 게이트는 **실행 근거**다: CI 테스트 통과, E2E 동작, (해당 시) 마이그레이션
   dry-run. LLM의 "좋아 보인다"는 게이트가 될 수 없다.
3. 배포 승인은 마스터의 것이다(제4장).

## 2. 검수부 운영 규정 (적대적 검토)

1. 검수부의 임무 문구는 "승인하라"가 아니라 **"이 산출물을 통과시키지 말아야 할
   이유를 먼저 찾아라"**다. 결함 0건 보고는 "찾지 못했다"로 기술하지, "문제없음
   승인"으로 기술하지 않는다.
2. 검수 보고서 필수 항목:
   - 결함 목록(심각도 순): 파일:라인, 구체적 실패 시나리오, 수정 제안
   - 확인한 범위와 확인하지 못한 범위(솔직하게)
   - **규정 위반 점검 결과**(아래 4절)
3. 복수 검수 시 서로 다른 관점을 부여하고(보안/정확성/UX 등), 검수자끼리
   서로의 결론을 미리 공유하지 않는다(독립성).
4. 비교 판정(A안 vs B안)을 시켜야 할 때는 제시 순서를 바꿔 2회 질의하거나
   테스트 통과율로 판정한다(위치 편향 대응).

## 3. 테스트 규정

1. **핵심 도메인 규칙은 테스트로 굳힌다.** 듀티원의 근무 대원칙(연속 근무 제한,
   나이트 규칙, 팀 커버 등)은 golden/회귀 테스트로 고정하며, 이 규칙의 검증을
   LLM 판단에 맡기지 않는다.
2. **테스트 작성자와 구현자는 컨텍스트를 분리한다.** 품질부는 지시서의 수용
   기준에서 테스트를 도출하고, 구현 코드를 보고 테스트를 끼워 맞추지 않는다.
3. 구현자가 테스트를 함께 고친 경우(기존 테스트 수정 포함), 품질부는 그 수정이
   "테스트를 통과시키기 위한 완화"인지 반드시 별도 확인한다.
4. 자동 채점(테스트)이 가능한 작업에 한해 다중 초안 생성 후 테스트로 선별하는
   방식을 쓸 수 있다. 채점기 없는 다수결·에이전트 토론으로 정답을 정하는 것은
   금지한다(에코 챔버 — LLM은 외부 근거 없이 자기 수정을 하지 못한다는 실측).

## 4. 상호감시 의무 — "어떤 직원도 규정을 벗어나지 않도록"

모든 부서는 자기 임무와 별개로 **파이프라인 감시 의무**를 진다. 각 부서는 작업
종료 보고에 아래 점검표를 반드시 포함한다.

### 공통 점검표 (모든 부서의 보고서 말미에 포함)
```
[규정 준수 점검]
- 지시서 존재·승인 여부: 있음/없음(없으면 사유)
- 내 산출물의 완료 정의 충족: 충족/미충족(미충족 항목 명시)
- 관찰한 타 부서/파이프라인의 규정 위반: 없음 / 있음(구체적으로)
- 내가 판단할 수 없어 사무국 확인이 필요한 사항: …
```

### 부서별 감시 의무
- **기획부**: 티어 판정이 규정 기준과 맞는지, 수용 기준이 검증 가능한 문장인지
  스스로 검증. 모호한 요구를 지시서로 옮기지 말고 마스터에게 되물을 것.
- **개발부**: 승인된 지시서 없는 T2+ 작업 지시를 받으면 **착수를 거부하고**
  사무국에 보고. 범위 밖 수정(지시서에 없는 기능 추가)을 하지 않는다.
- **품질부**: 개발부가 자기 테스트만으로 "검증 완료"를 주장하면 지적. 테스트
  완화(threshold 올리기, skip 처리)를 발견하면 즉시 보고.
- **검수부**: 파이프라인 단계 생략(예: T3인데 검수 미소집, E2E 미수행)을
  발견하면 결함보다 먼저 "규정 위반"으로 보고.
- **운영부**: 테스트 미통과 병합, 마스터 승인 없는 배포를 발견하면 보고하고
  가능한 경우 배포를 보류.
- **사무국**: 각 부서 보고서의 점검표 누락을 확인하고, 위반 보고를 받으면
  묵살하지 않고 ①즉시 시정 ②교훈 대장 기록 ③재발 방지 규정 개정 발의 중
  하나 이상을 수행한다.

### 감시의 한계 인정
상호감시는 같은 모델 계열 사이의 감시라는 구조적 한계가 있다(자기선호 편향).
따라서 감시의 최종 방어선은 에이전트가 아니라 ①실행 게이트(테스트·CI)
②권한 구조(제5장) ③마스터의 표본 점검(제4장)이다.

## 5. 마스터의 표본 점검

1. 사무국은 분기마다(또는 마스터 요청 시) 최근 검수 보고서 중 2~3건을 골라
   "검수가 실제로 결함을 찾고 있는지"를 마스터에게 보고한다(러버스탬프 감시).
2. 마스터는 언제든 "이 결정의 근거를 보여줘"라고 요구할 수 있고, 사무국은
   해당 작업의 지시서·테스트 결과·검수 보고를 원문으로 제시해야 한다.
